# Glossary

> Keep domain + architecture terms here so naming stays consistent across specs,
> code, and conversations with Claude. Add a line whenever a new term appears.

| Term | Definition |
|------|------------|
| **Context-mesh** | The overall architecture: a network of independent pods queried and correlated by an orchestrator. Two layers — *design-time* (this repo) and *runtime* (live data). |
| **Pod** | A self-contained unit of stored data owning a coherent slice, in whatever store type best fits it. Emergent — created/refined by the system, not predefined. |
| **Orchestrator** | The "primary pod" / front door: interprets a query, routes to pod(s), correlates results, returns the answer. |
| **Pod-registry** | The runtime, self-maintained map of all pods (what each owns, freshness, stats, lifecycle). The orchestrator's source of truth for routing. |
| **Policy** | An English-first rule set governing behavior. The five: storage-strategy, pod-formation, refinement-loop, correlation, data-governance. |
| **Refinement loop** | The feedback cycle that reshapes storage/routing based on streamed events and query outcomes. |
| **Event** | A unit of incoming data streamed into the mesh and stored in a pod. |
| **Correlation** | Combining results from multiple pods into one coherent answer. |
| **Tenant** | A customer/org owning a fleet of one or more clusters (ADR 0022). Rows in tenant-scoped tables (`service_dependencies`, `cluster_services`) carry `tenant_id`; single-deployment installs default to `DefaultTenantID`. |
| **Fleet cluster** | One of a tenant's Kubernetes clusters, represented by an `Integration` row (`ID` doubles as `cluster_id`). A tenant can own several. |
| **Hub** | Shorthand used throughout the fleet docs for **the central Go backend** (`src/backend/`, one process, RDS Postgres behind it) — as opposed to **Discovery**, which runs once per cluster. Every fleet-facing endpoint (`/api/cluster-inventory`, `/api/service-dependencies`, `/api/collector/connect`, `/api/live-fetch`, `/api/resolve-cluster`) is a Hub endpoint; Discovery only ever calls out to it, never the reverse. |
| **Discovery (`agentify-discovery`)** | The deterministic, non-agentic, **per-cluster** collector (ADR 0022 Decision #6) — one Deployment inside each fleet cluster. Everything it does is a read against *its own* cluster's K8s API, followed by a push or relay to the Hub: (1) lists namespaces/services/workloads and mines a service-dependency graph from pod logs, pushing both to the Hub on a timer; (2) holds one persistent outbound connection to the Hub and, over it, answers on-demand `live_*` reads (pods, logs, events, certs) the Hub relays from the agent. Never runs Claude/LLM calls, never receives an inbound connection from the Hub. |
| **CollectorToken** | The bearer credential **Discovery** presents when pushing to **the Hub** — resolved Hub-side via `resolveTenantContext` to `(tenant_id, cluster_id)`. Since [ADR 0027](decisions/0027-merge-k8fy-adapter-into-discovery.md) merged the old k8fy-adapter's separate `BACKEND_AUTH_TOKEN` into it, this is the single unified credential for every collector-facing endpoint, including `/api/ingest`. Distinct from `Integration.Token` (a still-stored-but-no-longer-consumed field, historically the Hub's *outbound* credential to the now-retired adapter log-server — conflating the two directions would have let a leaked outbound token grant inbound push access). |
| **`resolveTenantContext`** | A **Hub-side** helper (`handlers.go`) every collector-facing endpoint calls to identify which cluster/tenant is calling in: absent credential → `(DefaultTenantID, "")` (today's single-cluster behavior, unchanged); unrecognized credential → rejected (401); valid `CollectorToken` → that `Integration`'s `(tenant_id, cluster_id)`. Discovery never calls this itself — it's what the Hub runs *on* Discovery's request. |
| **Service→cluster resolver** | Split across two sides: the agent calls `resolve_service_clusters(namespace, service, backend_url)`, which is answered by **the Hub's** `GET /api/resolve-cluster` reading the `cluster_services` registry table (ADR 0023) — a table **Discovery** populates as a side effect of its own inventory push, not a separate query Discovery serves. Answers "which fleet cluster(s) run this service?" — 0/1/N matches; N is surfaced to the diagnosing skill as a fan-out, never silently resolved to one. |
| **Live drill-down / `CollectorHub`** | The **Hub-side** connection registry (`internal/api/collector_hub.go`) and `POST /api/live-fetch` relay (ROADMAP P18 use case #9, ADR 0022 Decision #7). The Hub holds the registry and does the relaying; **Discovery** holds the other end of the connection and does the actual K8s read once a request arrives over it. Lets the agent ask a specific fleet cluster's Discovery for a real-time K8s read (pods, logs, events, certs) without the Hub ever holding standing per-cluster credentials. |
| **Cluster-aware pod ID (`models.PodID`)** | A **Hub-side** fix (ADR 0024) for ingested-data (`current_state`/`events`) isolation — nothing Discovery does or is aware of. A pod ID optionally embeds `cluster_id` (`"k8fy.live-state.cluster-42.payments"` vs. the legacy `"k8fy.live-state.payments"`). Isolation is achieved by which pod ID a Hub query targets, not by a tenant WHERE-clause/RLS on those two tables — deliberate, see ADR 0024's "Isolation mechanism" section. |
| **Pattern A** | A skill strategy (spec 010, ADR 0017): deterministic parallel pre-fetch of every predictable signal, then exactly one Claude call — no agentic tool-calling loop. All core K8fy skills (`HealthSkill`, `CertAuditSkill`, `DiagnoseSkill`, `ChangeHistorySkill`, `RestartTrendSkill`) use this; only the `K8fyAgent` fallback still runs an agentic loop (Pattern B). |
